# GAPAK Front — Authentication Integration Report

## Scope

This phase connects the existing Vercel React frontend authentication boundary to the authoritative GAPAK Go/Fiber backend contract in `docs/BACKEND_FRONTEND_CONTRACT.md`.

Backend was not modified and no mock/fake authentication path was introduced.

## Implemented

### Session bootstrap

- `GET /api/v1/auth/csrf` bootstraps the CSRF token and records whether the server reports an existing session.
- Existing access token is memory-only.
- If no access token exists but the server reports a session, the client performs a single-flight `POST /api/v1/auth/refresh` using the HttpOnly refresh cookie.
- Session hydration then reads `GET /api/v1/users/me`.
- Failed refresh clears the in-memory access token and does not enter a refresh loop.

### Login

Uses exactly:

`POST /api/v1/auth/login`

Request fields are the backend fields:

- `login`
- `password`
- optional `totpCode`
- optional `deviceName`
- optional `deviceFingerprint`

The UI now exposes an optional authenticator-code field instead of using a fabricated `requires2FA/challengeId` response flow. The backend contract explicitly states that login handles TOTP directly and does not return a special successful 2FA challenge response.

### Registration

Normal registration uses:

`POST /api/v1/auth/register`

Email is preserved. `preferAnonymous` is explicitly `false` unless an explicit caller chooses otherwise; the AuthContext forces normal registration to `false`.

Anonymous registration uses only:

`POST /api/v1/auth/register-anonymous`

No anonymous mode is silently enabled for normal registration.

### Refresh

Uses:

`POST /api/v1/auth/refresh`

The refresh credential remains an HttpOnly cookie. The browser uses `credentials: include`; JavaScript never reads or stores the refresh token.

Concurrent refresh requests are single-flight: one network refresh is in flight and callers share its promise.

### CSRF

All authentication mutations are CSRF protected through the existing transport and `withCsrfRecovery` boundary.

On a CSRF rejection (`403` with a CSRF error code), the client obtains a fresh CSRF token once and retries the rejected operation. It does not blindly retry arbitrary mutation failures.

2FA setup, verification, disable, login, register, anonymous register, password reset, OAuth start, and logout are covered by the CSRF boundary where the backend requires mutation protection.

### Logout

Normal logout:

`POST /api/v1/auth/logout` with `{ allDevices: false }`

All-device logout:

`POST /api/v1/auth/logout` with `{ allDevices: true }`

No `/logout-all` endpoint was introduced.

Local authentication state is cleared in the cleanup path after logout attempts so a failed server logout cannot leave a valid access token in memory. Server failure remains observable to the caller.

### OAuth

OAuth initiation uses:

`GET /api/v1/auth/oauth/:provider`

The returned URL is validated before navigation and then opened with `window.location.assign`.

The backend callback is **not** treated as a JSON API. The authoritative callback is:

`GET /api/v1/auth/callback/:provider`

and is handled by the backend as an HTTP redirect. The frontend no longer POSTs the callback as `{ code }` and no longer fabricates an OAuth auth response.

Redirect URLs must use HTTPS in production. Plain HTTP is accepted only for local development hosts.

### 2FA management

Real backend endpoints are used:

- `POST /api/v1/auth/2fa/setup`
- `POST /api/v1/auth/2fa/verify`
- `POST /api/v1/auth/2fa/disable`

No challenge ID is invented or persisted by the frontend.

## Security properties

- refresh tokens are never stored in localStorage/sessionStorage;
- access tokens remain memory-only;
- CSRF token remains memory-only;
- request IDs are generated by the transport;
- auth tokens are not written to telemetry;
- OAuth callback is not converted into a fabricated client-side JSON response;
- unknown backend roles fail closed to the least-privileged UI role instead of receiving elevated permissions;
- UI-only profile fields are not fabricated from auth DTOs.

## Contract corrections made

1. Removed the obsolete frontend OAuth POST-callback flow.
2. Removed the obsolete `requires2FA/challengeId` authentication success model.
3. Login now passes the backend-supported `totpCode` directly.
4. Fixed the refresh route guard to recognize `/auth/refresh` correctly.
5. Removed the old unused auth schema that modeled the fabricated 2FA challenge response.
6. Updated the development sandbox so it does not submit fabricated credentials or OTP values.
7. Kept normal registration explicitly non-anonymous.
8. Kept logout-all on the real `/auth/logout` endpoint.

## Remaining auth integration blocker

The existing backend WebSocket route is separately blocked for browser authentication because its HTTP upgrade middleware requires a Bearer `Authorization` header, which browser `WebSocket` cannot set. This is deliberately not solved by putting access tokens into a URL. It belongs to the realtime integration phase and may require a backend-compatible handshake change.
