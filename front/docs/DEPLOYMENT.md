# GAPAK Front — Vercel production deployment

## Build architecture

GAPAK Front is a **Vite + React** application. It does not use Next.js, so `NEXT_PUBLIC_*` variables are not used. Vite exposes only variables prefixed with `VITE_`.

The only production frontend variables required are public service endpoints:

```env
VITE_API_BASE_URL=https://gapak-api-production.up.railway.app
VITE_WS_BASE_URL=wss://gapak-api-production.up.railway.app/ws
VITE_MEDIA_BASE_URL=https://gapak-api-production.up.railway.app
VITE_ENVIRONMENT=production
VITE_ENABLE_MOCK_API=false
VITE_ENABLE_PLATFORM_SANDBOX=false
```

Do **not** place JWT signing secrets, refresh tokens, database credentials, Redis credentials, storage credentials, OAuth client secrets, private keys, or encryption keys in Vercel environment variables.

## Authentication

Browser HTTP requests use `credentials: include`. Session credentials are backend-issued HttpOnly cookies. CSRF protection uses the memory-only token sent as `X-CSRF-Token`.

The native WebSocket client does not put an access token in the URL. The backend `/ws` route authenticates using the HttpOnly `gapak_at` cookie.

## Production origins

The supplied backend production configuration identifies:

- Frontend: `https://gapak.vercel.app`
- API: `https://gapak-api-production.up.railway.app`
- WebSocket: `wss://gapak-api-production.up.railway.app/ws`

Railway must allow the exact frontend origin through `CORS_ORIGINS`; credentials cannot be used with `*`.

## Cross-site cookies

Because Vercel and Railway are different sites, the backend production environment must use:

```env
COOKIE_SECURE=true
COOKIE_SAME_SITE=none
COOKIE_DOMAIN=
```

The frontend does not set these values. Do not set a Railway cookie Domain to the Vercel hostname.

The checked-in backend `.env.production.example` already expresses the required `SameSite=None` configuration. The separate Railway deployment guide contains an outdated `COOKIE_SAME_SITE=lax` example; the live Railway environment must follow the backend production validation rule (`none` for this cross-site deployment).

## CSP / security headers

`vercel.json` provides:

- HSTS
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- strict referrer policy
- restrictive permissions policy
- CSP with exact Railway API/WSS connect targets
- `frame-ancestors 'none'`
- `object-src 'none'`
- `upgrade-insecure-requests`

If the production media service moves to a different origin, update `img-src`, `media-src`, and any required `connect-src` target before deployment.

## OAuth

OAuth remains a top-level browser navigation to the backend-provided authorization URL. The backend callback is the authoritative callback endpoint and redirects back to the frontend. No OAuth client secret is shipped to Vercel.

## Media

The frontend consumes backend/object-store signed media URLs. It does not contain storage signing secrets. Signed URLs must be generated by the backend and treated as untrusted external resource URLs by the frontend.

## Vercel settings

- Framework preset: Vite / static frontend build
- Build command: `npm run build`
- Output directory: `dist`
- Install command: `npm ci`
- Root directory: `frontend` if the repository is deployed as a monorepo
- Production environment variables: use the `VITE_*` values above

After changing any `VITE_*` value, create a new Vercel deployment because Vite embeds these values at build time.

## Browser verification requirement

A successful local build or fetch unit test does not prove cross-site browser cookies, CORS, OAuth redirects, CSP, or WSS authentication. Use `docs/VERCEL_RAILWAY_INTEGRATION_REPORT.md` as the staging release checklist and execute it from a real HTTPS browser deployment.
