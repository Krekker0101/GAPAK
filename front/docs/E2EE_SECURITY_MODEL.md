# GAPAK E2EE Security Model

**Status:** Phase 3 frontend security boundary
**Protocol:** `gapak-e2ee-v1`

## 1. Protocol identity

GAPAK uses a **custom E2EE protocol** named **GAPAK E2EE protocol v1**.

It is **not Signal Protocol**, does not implement Double Ratchet, and does not claim X3DH/PQXDH semantics.
The implementation uses standard Web Crypto primitives, but composition of primitives into a protocol does not make the protocol Signal.

The frontend therefore fails closed where a guarantee requires backend-authenticated state that the current backend contract does not expose.

## 2. Cryptographic primitives

- ECDH P-256 for recipient key agreement.
- HKDF-SHA-256 for key derivation and domain separation.
- AES-256-GCM for authenticated encryption.
- ECDSA P-256/SHA-256 for sender-device signatures.
- 12-byte random AES-GCM nonces generated by `crypto.getRandomValues`.
- 32-byte random HKDF salts for per-recipient key wrapping.
- Web Crypto `CryptoKey` objects for local private-key use.

The protocol intentionally separates:

1. device identity/signing keys;
2. device agreement keys;
3. per-message symmetric encryption keys;
4. per-recipient wrapping keys.

## 3. Wire message construction

The send pipeline is:

`compose → resolve recipient devices → validate trust → generate message key → encrypt plaintext with AES-GCM → wrap message key for every recipient device → sign canonical envelope → send with idempotency key → acknowledge → persist status`

The network envelope contains `content: null`. Plaintext is not permitted on the wire.

The authenticated data binds the message to:

- protocol version;
- chat ID;
- sender user ID;
- sender device ID;
- sender key ID;
- message ID;
- sender-device sequence counter;
- key version;
- content type;
- creation timestamp.

## 4. Trust model

Trust is server-authenticated and represented by exactly five states:

- `VERIFIED` — accepted for encrypted sending.
- `UNVERIFIED` — rejected for encrypted sending.
- `CHANGED` — rejected until the new identity is verified.
- `REVOKED` — rejected permanently for the current key/device identity.
- `UNKNOWN` — rejected because trust cannot be established.

### Fail-closed rule

**Only `VERIFIED` devices are eligible encryption recipients.**

There is no automatic downgrade from `VERIFIED` to an implicitly trusted state, and no fallback to plaintext.

A recipient user with multiple devices is eligible only when **every currently registered recipient device returned by the backend is `VERIFIED`**. This prevents silently encrypting for only a subset of a user's devices while pretending that all devices are protected.

## 5. Device model

The target model is:

```text
User
├── Device A
│   ├── identity key
│   ├── agreement key
│   └── signing key
├── Device B
│   ├── identity key
│   ├── agreement key
│   └── signing key
└── Device C
    ├── identity key
    ├── agreement key
    └── signing key
```

Keys are per-device and are never shared between devices.

The client can locally generate and persist its private keys. However, a secure multi-device deployment additionally requires the backend to authenticate the public-key binding to the account/device and to expose all active device bundles.

## 6. Key storage

Private keys are stored in IndexedDB as non-extractable `CryptoKey` objects after local key generation.

The current browser limitation is important: Web Crypto requires the generated key pair to be exportable if the application needs to export public JWK metadata using the standard API. GAPAK minimizes exposure by exporting private JWK material only long enough to immediately re-import it as non-extractable. The private JWK is not persisted.

### Threat model

IndexedDB is protected by the browser origin security model, not by a user password or a hardware security module. A same-origin XSS compromise can potentially invoke the application's cryptographic operations. Therefore CSP, dependency integrity, origin isolation and secure deployment remain part of the E2EE threat model.

## 7. Key rotation

The frontend has local key-generation capability, but **authoritative device key rotation is not enabled without a backend contract**.

A safe rotation requires:

1. authenticated request by the current device;
2. new key version;
3. server-side atomic replacement;
4. old-key revocation timestamp/version;
5. updated recipient bundles;
6. trust-state transition;
7. protection against rollback to the previous key version.

The client intentionally refuses partial client-only rotation.

## 8. Device registration

The current frontend can generate a device identity locally, but it does not claim that the device is registered merely because local keys exist.

Backend requirements:

- bind account ID to device ID;
- bind identity public key, agreement public key and signing public key;
- assign a monotonic key version;
- authenticate the registration request;
- return canonical device state;
- expose revocation state;
- expose the device to the authenticated account's device list.

Until those fields are available, the registration boundary fails closed rather than submitting an incomplete key record.

## 9. Signing and verification

Every outbound message is signed by the sender device's signing key over the canonical envelope.

The recipient verifies the signature before decrypting the message body.

Signature verification alone does not establish trust. The sender device must also have an accepted backend trust state.

## 10. Replay and duplicate protection

Each sender device receives a monotonic message sequence counter persisted in IndexedDB. The message ID is also unique.

The frontend rejects a message ID that has already been processed for the target device.

This is only a client-side safety boundary. **The backend must enforce replay protection authoritatively** using at least:

- sender device ID;
- message ID;
- sender sequence counter;
- key version;
- chat membership;
- revocation state.

The backend must reject duplicate or stale counters even if an attacker bypasses the browser client.

## 11. Realtime security

Realtime frames must have:

- server-issued event ID;
- event type;
- timestamp;
- typed payload;
- optional correlation ID;
- optional version.

Message acknowledgement and delivery status must be idempotent by message/client ID.

The frontend deduplicates event IDs and rejects malformed frames. Durable server replay/cursor semantics are still required for complete reconnect guarantees.

## 12. Offline messaging

Offline persistence stores **already encrypted message envelopes**, never plaintext composer content.

The queue is bounded by item count and serialized byte size.

When capacity is reached, the client **does not evict an older message**. It raises an explicit error.

Permanent send failures remain queued for explicit user-visible recovery rather than being silently discarded.

## 13. Metadata limitations

E2EE does not hide all metadata. The backend may still observe, depending on its contract:

- account/device IDs;
- chat membership;
- message size;
- message timing;
- delivery/ack timing;
- IP/network metadata;
- ciphertext and encrypted attachment metadata.

The current protocol does not provide metadata privacy equivalent to specialized privacy-preserving messaging systems.

## 14. Forward secrecy and post-compromise security

The current GAPAK protocol **does not provide a Double-Ratchet-equivalent forward-secrecy or post-compromise-security guarantee**.

Per-message random AES keys and ephemeral ECDH wrapping improve key separation, but they do not substitute for a ratcheting protocol.

If GAPAK requires those properties, the protocol must be redesigned around a formally specified ratchet rather than adding ad-hoc counters to this construction.

## 15. Recovery semantics

There is currently no safe client-only recovery from loss of the device's private keys.

A secure recovery design must specify:

- new-device enrollment;
- old-device revocation;
- re-verification;
- key-change notification;
- historical message availability;
- account recovery compromise resistance.

The frontend must not silently regenerate keys for an existing registered device and continue as if the identity were unchanged.

## 16. Backend requirements blocking full production E2EE

The frontend cannot independently implement these guarantees:

1. authenticated device registration;
2. complete per-device recipient bundle retrieval;
3. server-authoritative trust state;
4. key version and rollback protection;
5. device revocation enforcement;
6. key rotation;
7. replay/counter enforcement;
8. message acknowledgement/idempotency semantics;
9. reconnect replay/cursor semantics;
10. server-side verification of sender device membership/trust;
11. safe encrypted attachment key wrapping and streaming upload;
12. audited recovery semantics.

These are release blockers for claiming complete secure multi-device E2EE.

## 17. Logging policy

The cryptographic layer must never log:

- plaintext message bodies;
- private keys/JWK private material;
- AES/message keys;
- ECDH shared secrets;
- session secrets;
- access tokens;
- refresh tokens.

Telemetry must contain identifiers and status/error codes only, with sensitive values redacted.

## 18. Security conclusion

Phase 3 establishes a **fail-closed GAPAK E2EE frontend boundary**. It does not claim to have transformed the protocol into Signal or another standardized secure messaging protocol.

Production release should describe the feature as **GAPAK E2EE protocol v1** only after the backend requirements in this document are implemented and independently tested.
