# GAPAK Backend — GAPAK E2EE Integration Report

Date: 2026-08-12

## Scope

This report covers the production HTTP integration between the existing GAPAK Frontend and the Go/Fiber backend for encrypted chat, trusted devices, and prekeys. The authoritative name is **GAPAK E2EE protocol**.

The implementation is a custom protocol v1. It is a custom protocol v1 and does not claim a standardized ratcheting protocol implementation.

## Backend hardening completed

### Message endpoint

`POST /api/v1/chats/:chatId/messages`

The backend now requires:

- authenticated user and chat membership;
- `senderDeviceId`;
- sender device owned by the authenticated user;
- sender device not revoked and canonical backend trust state `TRUSTED`;
- `senderKeyId = <senderDeviceId>:identity:v1`;
- `encryptionProtocol = TRUSTED_CHAT`;
- exact GAPAK E2EE v1 encryption algorithm string;
- non-empty hexadecimal ciphertext;
- 12-byte hexadecimal nonce;
- 64-byte hexadecimal `authenticationTag` field (wire-compatible ECDSA-P256 signature field; it is not an AES-GCM tag);
- at least one per-device key envelope;
- recipient user is a current chat member;
- recipient device exists, belongs to the recipient user, is not revoked, and is `TRUSTED`;
- envelope key version 1 and recipient identity key id;
- valid public JWK material without private-key fields;
- valid encrypted recipient envelope structure;
- plaintext content must remain empty.

The server never decrypts user plaintext.

### Server-generated identifiers and timestamps

The persisted message primary key and persisted timestamps are created by the backend. `clientMessageId` remains an idempotency/correlation key supplied by the client and is not the authoritative message ID.

Duplicate `clientMessageId` retries return the original message only when the encrypted message fields match. Reusing the same client ID for a different ciphertext, nonce, sender device, algorithm, or counter returns `409 chats.e2ee.replay_conflict`.

### Replay protection

The backend rejects reuse of a sender-device `ratchetCounter` with `409 chats.e2ee.replay_detected`. The check is transaction-scoped and serialized through a PostgreSQL advisory transaction lock.

### Trusted devices

Endpoints:

- `POST /api/v1/chats/trusted-devices`
- `GET /api/v1/chats/trusted-devices`
- `DELETE /api/v1/chats/trusted-devices/:deviceId`

Canonical backend trust states remain:

- `TRUSTED`
- `UNVERIFIED`
- `REVOKED`

No parallel backend trust enum was introduced. The existing frontend may display its own UI state, but `TRUSTED` is backend-authoritative.

Device registration requires valid EC P-256 public JWKs for identity and signing keys. Private key material is rejected. Device IDs are generated by the backend and returned to the client.

Revocation changes the canonical state to `REVOKED` and invalidates message sending/prekey publication from that device. Database foreign keys cascade prekeys when a device record is actually removed.

### Prekeys

Endpoints:

- `POST /api/v1/chats/trusted-devices/:deviceId/pre-keys`
- `GET /api/v1/chats/pre-key-bundles/:userId`

The path parameter is authoritative. The backend does not require a query-string `userId`.

Published prekeys must contain valid EC P-256 public JWK material. One-time prekeys require a future expiry timestamp. Expired prekeys are excluded from bundles. One-time prekeys are consumed transactionally when a bundle is issued.

### Security logging

No plaintext, private keys, session keys, or encryption secrets are logged by the chat/E2EE service.

## Current frontend compatibility findings

Two existing frontend/backend protocol mismatches prevent a truthful `READY` verdict without violating the user's requirement that backend IDs/timestamps remain authoritative.

### Blocker 1 — message ID in authenticated encryption context

The current GAPAK Frontend creates an envelope UUID locally and includes it in the authenticated data and signature. The frontend then maps that UUID to `clientMessageId` while the backend creates a distinct persisted message `id`.

The recipient-side frontend verifies the authenticated data using the backend response `message.id`. Therefore, a distinct server-generated `message.id` makes the authenticated data differ from the data used during encryption.

The backend cannot safely repair this by replacing its ID with the client ID, because that would violate the server-authoritative ID requirement.

### Blocker 2 — client timestamp in authenticated encryption context

The current GAPAK Frontend includes its locally-created `createdAt` value in authenticated data and uses it during encryption/signature generation. The backend persists a server-side `createdAt` timestamp.

The recipient-side frontend reconstructs authenticated data using the backend `createdAt`. A different persisted timestamp therefore causes authenticated decryption failure.

The backend cannot safely solve this by persisting the client timestamp as the authoritative database timestamp.

### Blocker 3 — trust-state representation in current frontend

The backend canonical state is `TRUSTED`, as required by the data model. The current frontend crypto mapper recognizes `VERIFIED`, `UNVERIFIED`, `CHANGED`, `REVOKED`, and `UNKNOWN`, but does not map backend `TRUSTED` to its UI-level verified state.

The backend must not invent `VERIFIED` as a second authoritative backend state. The mismatch is therefore documented rather than masked.

## Compatibility contract

### Request fields

`clientMessageId`: client retry/correlation key; not authoritative message ID.

`senderDeviceId`: backend-issued trusted-device UUID.

`ciphertext`: hexadecimal encrypted payload.

`nonce`: 12-byte hexadecimal AES-GCM nonce.

`senderKeyId`: `<deviceId>:identity:v1`.

`authenticationTag`: 64-byte hexadecimal ECDSA-P256 signature carried under the existing wire field name; not an AES-GCM authentication tag.

`keyEnvelopes[]`: one envelope per recipient device.

`content`: must be empty/omitted for the encrypted production path.

### Response authority

The backend is authoritative for:

- `id`;
- `sequenceNumber`;
- `sentAt`;
- `createdAt`;
- `updatedAt`;
- `senderId`;
- `senderDeviceId`;
- persisted trust/device state.

## Verdict

**E2EE CONTRACT: NOT READY** — backend-side hardening is complete, but the existing frontend's authenticated encryption context is coupled to client-generated message ID and timestamp, while the required production contract makes those values backend-authoritative.

**TRUST MODEL: READY** — backend canonical state remains `TRUSTED` / `UNVERIFIED` / `REVOKED`, with revoked-device enforcement.

**DEVICE MODEL: READY** — device IDs are server-generated, ownership/revocation/trust are enforced, and private key material is rejected.

**PREKEY MODEL: READY** — public JWK validation, expiry rules, one-time consumption, ownership, and revoked-device checks are enforced.

### Encrypted message edits

`PATCH /chats/messages/:messageId` also remains encrypted-only. It now requires a valid ciphertext, nonce, and `authenticationTag`, rejects plaintext content, preserves the GAPAK E2EE algorithm contract, updates the persisted authentication signature field, and refuses edits from revoked/untrusted sender devices.
